Warum Claude Code CLI als Coding Agent in v1
Drei sachliche Gründe:

Du kennst es schon. Aus deinem Hintergrund — /loop, headless mode, Worktree-Parallelisierung, Subagenten — bist du in der Claude-Code-CLI näher an "fließend" als bei Alternativen. Das beschleunigt M1 um Wochen, weil du nicht parallel zu forge ein neues Tool lernst.

Es löst genau das, was forge braucht. Headless mode (claude -p) ist als Subprozess-API gebaut. --allowedTools, --max-turns, --output-format json, --cwd, --permission-mode — das sind genau die Stellschrauben, die forge an seinem Coding-Agent braucht. Ohne dieses CLI müsstest du die Tool-Use-Loop, das Edit-Tooling, das File-Reading selbst implementieren — das ist Wochen Arbeit ohne Mehrwert.

Worktree-Native. Claude Code arbeitet sauber in einem --cwd <pfad> Worktree, ohne dass es globalen State zwischen Aufrufen mitnimmt. Das passt exakt zu forges Generation-Modell (jede Generation = neuer Worktree, sauberer Subprozess-Aufruf).

Wo die architektonische Grenze liegt
Hier kommt der wichtige Teil: Claude Code CLI ist in forge ein Plug-in, nicht das Fundament. Das ist kein Detail, sondern Designprinzip.

Konkret heißt das: Es gibt in forge-execute/ ein Interface — nennen wir es CodingAgent — das genau drei Methoden hat:

python
class CodingAgent(Protocol):
    async def propose(
        self,
        worktree: Path,
        prompt: str,
        allowed_paths: list[str],
        capabilities: Capabilities,
        budget_usd: Decimal,
        max_turns: int,
    ) -> ProposalResult:
        """Generiert Vorschlag im Worktree, returnt strukturiertes Result."""
        ...
    
    async def review(
        self,
        worktree: Path,
        diff: str,
        ...
    ) -> ReviewResult: ...
    
    async def estimate_cost(self, prompt_tokens: int) -> Decimal: ...
Und es gibt eine konkrete Implementierung ClaudeCodeCLIAgent, die das via Subprozess-Call umsetzt. Aber die Architektur ist so geschnitten, dass morgen ein CodexCLIAgent, OpenCodeAgent oder ein DirectAnthropicAPIAgent daneben treten kann, ohne dass forge-core oder forge-execute strukturell anders aussehen.

Warum die Trennung wichtig ist:

Lock-in vermeiden. Coding-Agent-Landschaft ändert sich schnell. Wenn du forge in 2 Jahren produktiv betreibst und Claude Code CLI in der Form nicht mehr existiert oder ein deutlich besseres Tool da ist, willst du tauschen können, ohne forge umzubauen.

Multi-Agent-Strategien später. Sobald du in Phase v3 (Loop 3) bist, ist die Modell- und Agent-Wahl Teil dessen, was die Fabrik lernt. Vielleicht stellt sich heraus, dass für lint_cleanup ein deutlich kleineres und billigeres Tool reicht. Die Architektur muss das tragen können.

Testbarkeit. Für Unit-Tests von forge-execute willst du einen MockCodingAgent, der deterministische Antworten gibt. Geht nur, wenn die Schnittstelle abstrakt ist.

Wie der Aufruf konkret aussieht
In v1 produktiv ist nur eine Implementierung — und die ist erstaunlich kurz:

python
class ClaudeCodeCLIAgent:
    def __init__(self, model: str = "sonnet"):
        self.model = model
    
    async def propose(self, worktree, prompt, allowed_paths, 
                     capabilities, budget_usd, max_turns):
        allowed_tools = self._build_allowed_tools(capabilities)
        
        env = {
            **os.environ,
            "ANTHROPIC_API_KEY": os.environ["ANTHROPIC_API_KEY"],
        }
        
        proc = await asyncio.create_subprocess_exec(
            "claude", "-p", prompt,
            "--output-format", "json",
            "--allowedTools", allowed_tools,
            "--max-turns", str(max_turns),
            "--cwd", str(worktree),
            "--model", self.model,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
            env=env,
        )
        
        try:
            stdout, stderr = await asyncio.wait_for(
                proc.communicate(),
                timeout=600,
            )
        except asyncio.TimeoutError:
            proc.kill()
            raise CodingAgentTimeout()
        
        result = json.loads(stdout)
        diff = await self._git_diff(worktree)
        
        return ProposalResult(
            diff=diff,
            tokens_in=result.get("usage", {}).get("input_tokens", 0),
            tokens_out=result.get("usage", {}).get("output_tokens", 0),
            cost_usd=self._compute_cost(result),
            stop_reason=result.get("stop_reason"),
            model_version=result.get("model"),
            raw_response=result,
        )
Das ist ungefähr 50-80 Zeilen Code. Die ganze Komplexität — Worktree-Management, Capability-Enforcement, Event-Emission, Cost-Caps — sitzt eine Schicht darüber im Runner. Der Coding-Agent macht nur eine Sache: Subprozess starten, Output parsen, Diff abholen.

Drei wichtige Punkte zur tatsächlichen CLI-Nutzung
--allowedTools ist dein Capability-Enforcement. Forges capabilities-Block aus der Spec wird in den --allowedTools-String übersetzt. Wenn merge_pr: false und push_to_main: false, dann darf in der Bash-Tool-Whitelist nichts mit gh pr merge oder git push stehen. Das ist die wichtigste Sicherheitsschicht — sie wirkt im CLI-Subprozess, bevor der Agent überhaupt was tun könnte.

Permission Mode. Claude Code CLI hat --permission-mode mit Werten wie default, acceptEdits, bypassPermissions. Für forge brauchst du bypassPermissions (oder das Äquivalent in der aktuellen Version), weil der Subprozess vollständig non-interaktiv läuft. Die Sicherheit kommt nicht aus interaktivem Bestätigen, sondern aus --allowedTools plus Worktree-Isolation plus Forbidden-Path-Validierung nach dem Run.

Hooks im Worktree. Du kannst .claude/hooks/ im Worktree setzen, die nur für diesen forge-Run aktiv sind. Konkret nützlich: ein PreToolUse-Hook auf Bash, der nochmal gegen die forbidden-Liste prüft. Das ist die zweite Verteidigungslinie nach --allowedTools und die erste, die innerhalb des Subprozesses wirkt.

Wo Claude Code CLI in v1 NICHT verwendet wird
Damit es ehrlich ist:

Nicht für PR-Erstellung. Das macht forge selbst via gh CLI. Begründung: PR-Body strukturiert generieren, Labels setzen, Reviewer assignen — das ist forge-Logik, nicht Coding-Agent-Logik.
Nicht für Eval. Eval ist ein simpler Shell-Command-Aufruf via subprocess.run(spec.eval_suites.quick.cmd). Kein LLM nötig.
Nicht für Score-Parsing. Auch das ist deterministisches Python.
Nicht für forge analyze. SQL-Queries auf DuckDB, Markdown-Generierung. Kein LLM.
Nicht für Loop-3-Tuning (in v3). Das sind Bandits und Bayesian Optimization, klassisches ML/Statistik. Auch kein LLM.
Der Coding-Agent — und damit Claude Code CLI — wird in v1 nur an genau zwei Stellen aufgerufen: im propose-Schritt jeder Generation, und im review_only-Trigger für PR-Reviews. Sonst nirgendwo. Das ist wenig, und das ist Absicht: die meiste Komplexität von forge ist orchestrierend, nicht generierend.

Zwischen Anthropic-API direkt und Claude Code CLI
Eine berechtigte Frage, die ich beim Spec-Schreiben offen gelassen habe: warum nicht direkt das Anthropic SDK gegen /v1/messages mit Tool-Use, statt den Subprozess-Umweg über CLI?

Die Antwort hat zwei Teile:

Pro direkte API: Mehr Kontrolle (Tool-Definitions, Streaming, structured outputs), keine Subprozess-Overhead, sauberere Integration in Async-Code, eigene Tool-Implementierungen.

Pro CLI-Subprozess (gewinnt in v1): Tool-Loop, File-Editing, Patch-Application, Git-Awareness sind in Claude Code CLI bereits produktiv-ausgereift. Wenn du das alles selbst implementierst, sind das ~2000 Zeilen Code für eine Funktionalität, die schon existiert. Plus: Claude Code CLI bekommt von Anthropic kontinuierlich Updates (bessere Patch-Application-Heuristiken, robustere Tool-Use-Loops), die du sonst selbst nachziehen müsstest.

Empfehlung für die CodingAgent-Schnittstelle in v1: CLI-Subprozess als einzige Implementierung, aber die Schnittstelle so geschnitten, dass eine direkte API-Implementierung in v2 oder später möglich ist. Wenn du in 6 Monaten merkst, dass dir Streaming, strukturierte Outputs oder bessere Cost-Telemetrie fehlen, ziehst du die zweite Implementierung hoch und schaltest pro Trigger zwischen ihnen um.

Praktisch heißt das für dich beim Bau: Halte die CodingAgent-Abstraktion in forge-execute/agents/ konsequent durch — auch wenn sie sich in v1 wie unnötiges Interface anfühlt, weil es nur eine Implementierung gibt. Der Tag, an dem du froh sein wirst, ist der Tag, an dem du die direkte API oder einen Konkurrenten testen willst, ohne forge umzubauen.

Soll ich die CodingAgent-Schnittstelle und die ClaudeCodeCLIAgent-Implementierung als ausgearbeitetes Modul-Design schreiben? Inklusive der Übersetzungslogik von forges capabilities-Block in den --allowedTools-String — das ist die Stelle, an der die Spec-Sicherheitsgarantien konkret werden.

Das Problem zuerst
CLAUDE.md ist die Verfassung des Coding-Agents — Build-Befehle, Test-Befehle, Architektur-Konventionen, Gotchas. Sie veraltet schneller als jede andere Datei im Repo, weil sie nicht von Code-Compilern, Linters oder Tests geprüft wird. Drei Drift-Quellen:

Code ändert sich, Doku nicht. Du benennst einen Service um, du fügst eine Migrationskommando hinzu, du wechselst von npm zu pnpm — CLAUDE.md weiß davon nichts. Bei der nächsten forge-Generation propose't der Agent einen Build mit npm install, der scheitert.

CLAUDE.md driftet weg von der project.yaml. In forge gibt es zwei Wahrheits-Quellen: die project.yaml (Surfaces, Forbidden, Capabilities) und die CLAUDE.md (qualitative Konventionen, Gotchas, Architektur-Hinweise). Wenn die beiden auseinanderlaufen, vertraut der Agent der einen oder anderen — Ergebnis ist nicht-deterministisch.

CLAUDE.md lernt nicht aus Fehlern. Wenn forge dreimal denselben Bug-Typ produziert (z.B. immer wieder await vor synchronen Calls vergisst), sollte das eigentlich als Gotcha in CLAUDE.md landen. Tut es aber nicht automatisch.

Die naheliegende, aber falsche Antwort
"Lass forge ihre eigene CLAUDE.md aktualisieren". Das ist verlockend, aber es bricht Prinzip 3 der Spec: forge optimiert nicht sich selbst und nicht ihre eigene Konfiguration.

Eine CLAUDE.md ist Teil der Konfiguration des Coding-Agents — wenn die Maschine sie selbst editiert, hat sie Einfluss auf ihr eigenes Verhalten in der nächsten Generation. Das ist genau die unkontrollierte Self-Improvement-Spirale, die wir vermeiden wollen.

Konkret: Stell dir vor, eine schlechte Generation schreibt in CLAUDE.md "ignoriere Type-Errors, sie sind oft falsch". Beim nächsten Run sieht der Agent das, glaubt es, ignoriert Type-Errors. Drei Tage später ist eine Lawine schwer reproduzierbarer Bugs im Repo. Niemand merkt's, weil niemand CLAUDE.md-Änderungen reviewt — sie ist ja "nur Doku".

Daraus folgt: CLAUDE.md muss ins Forbidden-Set. Sie ist forbidden für die Maschine, genauso wie .forge/project.yaml und .github/workflows/.

Die richtige Architektur: vier Schichten
Nachdem der naive Weg ausscheidet, brauchen wir ein durchdachtes Modell. Vier Schichten, jede mit klarer Verantwortung.

Schicht 1 — Statische Generierung aus Wahrheits-Quellen
Vieles in einer typischen CLAUDE.md ist eigentlich abgeleitete Information. Build-Befehle stehen in package.json und pyproject.toml. Test-Befehle stehen dort auch. Verzeichnisstruktur kann ein tree-Aufruf liefern. Surfaces und Forbidden stehen in project.yaml.

CLAUDE.md wird daher in Sektionen mit explizitem Status aufgeteilt:

markdown
# CLAUDE.md

<!-- AUTOGENERATED:START — section_id="build_commands" — do not edit by hand -->
## Build & Test Commands

- Backend tests: `cd backend && pytest -x -q`
- Backend lint: `cd backend && ruff check src/`
- Frontend tests: `cd frontend && npm test`
- Frontend type-check: `cd frontend && npx tsc --noEmit`
<!-- AUTOGENERATED:END -->

<!-- AUTOGENERATED:START — section_id="forge_surfaces" -->
## Surfaces & Forbidden Zones (from .forge/project.yaml)

You may edit:
- backend/src/services/
- backend/src/agents/tools/
- backend/agents/maler.yaml (only keys: system_prompt, tools, temperature)

You may NEVER edit:
- backend/src/routes/auth.py
- backend/src/routes/payments.py
- backend/migrations/**
<!-- AUTOGENERATED:END -->

<!-- HUMAN:START — section_id="architecture_notes" -->
## Architecture Notes

PINTA uses a dual-index Azure AI Search architecture...
<!-- HUMAN:END -->

<!-- HUMAN:START — section_id="gotchas" -->
## Known Gotchas

- The `quote_calculator.py` rounding uses banker's rounding,
  not the obvious round-half-up. Don't "fix" this.
- ...
<!-- HUMAN:END -->
Ein neuer CLI-Befehl forge sync-claude-md regeneriert ausschließlich die AUTOGENERATED-Blöcke, lässt HUMAN-Blöcke unangetastet. Läuft als Pre-Commit-Hook und in CI als Drift-Check. Wenn CI einen Drift erkennt (forge sync-claude-md --check exit code != 0), schlägt der Build fehl mit der Meldung "CLAUDE.md ist nicht synchron mit project.yaml — bitte forge sync-claude-md lokal ausführen".

Das ist deterministisch, sicher, und löst etwa 60% des Problems.

Schicht 2 — Vorschlagsmechanismus für Human-Sektionen
Die HUMAN:START-Blöcke können nicht autogeneriert werden, weil sie qualitatives Wissen enthalten. Aber sie können vorgeschlagen werden — und zwar als ganz normaler PR, der vom Menschen reviewt wird.

Konkret: Es gibt einen speziellen forge-Trigger claude_md_review, der wöchentlich oder auf manuellen Anstoß läuft. Er macht genau das:

Liest die Events der letzten N Tage aus dem Store
Identifiziert wiederkehrende Failure-Patterns aus GuardrailViolation, PreflightFailed, EvalFinished mit gates_passed=false
Identifiziert PRs, die nach Merge wieder revertet wurden (PRReverted)
Schlägt für die HUMAN:START — section_id="gotchas"-Sektion neue Einträge vor — als Diff in einem PR
Wichtig: Das Ergebnis ist immer ein Pull Request, niemals ein direkter Edit. Der Mensch reviewt, nimmt an, lehnt ab, oder editiert. Der entscheidende Punkt: derselbe Sicherheitsmechanismus wie für jeden anderen Code-Change — Two-Eyes-Principle.

Implementierungs-Hinweis: Dieser Trigger braucht in der project.yaml eine explizite Capability-Erweiterung. Standardmäßig ist CLAUDE.md forbidden. Der claude_md_review-Trigger läuft mit einem Spezial-Profil, das genau eine Datei editieren darf — CLAUDE.md — und nichts anderes:

yaml
triggers:
  on_demand:
    claude_md_review:
      strategy: review_only
      model: opus
      capabilities_override:           # NUR für diesen Trigger
        edit: ["CLAUDE.md"]            # extrem eng
        run: []                        # keine Shell-Aktionen
        commit: true
        open_pr: true
Dass diese Override-Möglichkeit überhaupt existiert, ist eine Schwächung von Prinzip 3 — aber eine kontrollierte. Der Mensch genehmigt jeden einzelnen Vorschlag, und der Trigger kann nur CLAUDE.md ändern, sonst nichts.

Schicht 3 — Validierung gegen Realität
Auch wenn CLAUDE.md aktuell aussieht, kann sie inhaltlich falsch sein. Der Test-Befehl steht drin, ist aber seit drei Wochen broken. Der Build-Pfad existiert nicht mehr.

forge doctor kriegt deshalb einen erweiterten Check --validate-claude-md, der:

Jeden Shell-Command aus den AUTOGENERATED-Blöcken probeweise ausführt (--dry-run wenn möglich, sonst gegen ein temp-Worktree)
Jeden Pfad-Verweis prüft (existiert er noch?)
Jeden Datei-Namen prüft (existiert er noch?)
Inkonsistenzen zwischen CLAUDE.md und project.yaml meldet
Läuft idealerweise als CI-Job auf jedem PR (auch auf forge-PRs!), und wöchentlich als scheduled Check.

Schicht 4 — Operator-Disziplin
Ein Teil bleibt nicht automatisierbar und das ist ehrlich so. Architektur-Entscheidungen, Domain-Wissen, "warum haben wir das so gebaut"-Kontext — das ist menschliche Verantwortung.

In Phase 3 der Spec (manuelle Analyse, Teil 10) gehört explizit hinzu: CLAUDE.md lesen und aktualisieren ist Teil der wöchentlichen 30-Minuten-Routine. Die forge analyze-Reports zeigen, wo die Maschine stolpert — der Operator entscheidet, ob ein Stolpern eine Gotcha-Notiz wert ist.

Was das in der Spec ändert
Drei Stellen in der forge-spec-v0.2.md müssen ergänzt werden:

Teil 5 — Projekt-Spezifikation: CLAUDE.md explizit als forbidden listen, capabilities_override als Konzept einführen für Spezial-Trigger.

Teil 7 — Sicherheit & Guardrails: Eine neue Sektion 7.6 über die kontrollierte Lockerung für eng umrissene Trigger wie claude_md_review. Mit der harten Regel: jede capabilities_override ist explizit, eng (genau eine Datei oder ein klar definierter Pfad), und produziert immer einen menschlich-reviewten PR.

Teil 9 — MVP: forge sync-claude-md als 11. Punkt aufnehmen, weil ohne diesen Befehl die CLAUDE.md schon ab dem ersten Sprint driftet.

Teil 10 — Manuelle Analysephase: Wöchentliche CLAUDE.md-Pflege explizit als Tätigkeit.

Konkret für PINTA, wenn du jetzt anfängst
Drei Dinge machst du in dieser Reihenfolge:

Heute (15 Minuten): Vorhandene PINTA-CLAUDE.md durchgehen und in Blöcke aufteilen. Was ist abgeleitete Information (→ AUTOGENERATED-Marker drum)? Was ist menschlicher Kontext (→ HUMAN-Marker drum)? Schon dieser Schritt allein bringt Klarheit.

In M1 (Schritt 4 deiner Implementierung): forge sync-claude-md als CLI-Subcommand bauen. Ist deutlich kleiner als die anderen Module — vielleicht 200 Zeilen Code. Liest project.yaml, generiert die AUTOGENERATED-Blöcke, ersetzt sie atomar in der CLAUDE.md.

Nach M1, bevor du claude_md_review als Trigger einbaust: mindestens 30 Runs Erfahrung sammeln. Erst dann hast du genug Failure-Patterns, dass ein automatischer Vorschlag-Mechanismus überhaupt sinnvolle Vorschläge generiert. Vorher generiert er Rauschen.

Eine ehrliche Anmerkung zum Schluss: Die CLAUDE.md-Frage ist eine von mehreren "Sub-Wahrheits-Quellen", die sich in einer reifen forge-Installation ähnlich verhalten werden. .cursor/rules/, AGENTS.md, Lint-Configs, Issue-Templates — alle haben dieselben Drift-Probleme. Das hier skizzierte Vier-Schichten-Modell (Generierung aus Wahrheits-Quellen + kontrollierter Review-Trigger + Validierung + Operator-Routine) ist ein Pattern, das du auf alle anwenden kannst.
